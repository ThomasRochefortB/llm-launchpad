# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project follows [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added
- vLLM deployments state their own concurrency instead of inheriting the image's. `--max-num-seqs` was never passed, and the pinned images disagree: 256 in the vLLM the Modal and Prime runtimes run, 1024 in the newer one Vast pins. The same deployment therefore decoded at four times the concurrency depending on where it landed -- and on a hybrid model that is not a tuning difference. Each decode sequence holds a recurrent-state block, so Qwen3.8 27B served happily on Modal and Prime and, on an otherwise identical Vast rental with more VRAM than either, refused to start: `max_num_seqs (1024) exceeds available Mamba cache blocks (674)`, after four minutes of paid startup. Advanced deploy grows a **Max concurrent sequences** field and `deploy`/`switch` grow `--max-num-seqs`; left blank, every provider now serves the same 256, which is what two of the three already did.
 `vllm serve` was launched without `--max-model-len`, so it always took the model's own maximum position count -- and vLLM refuses to start when the KV cache for that context does not fit, which means a 262k-context model could not be served on any GPU its weights alone fit on. Advanced deploy grows a **Max context tokens** field, `llm-launchpad deploy`/`switch` grow `--max-model-len`, and the value reaches Modal (through `MAX_MODEL_LEN`), Prime and Vast alike. The form's VRAM estimate restates itself at the requested context rather than at the model's maximum, so the number that decides the GPU is the number the endpoint will actually serve, and the same figure is what OpenCode is told the context limit is.
- Vast model downloads now show percentage, downloaded/total GB, transfer speed, and an estimated remaining time in one updating summary row. Totals come from Hugging Face file metadata and include completed shards; unavailable metadata falls back to transferred bytes. Provisioning distinguishes reported image pulls from waiting for SSH, and only marks the machine ready after SSH succeeds.
- `llm-launchpad prime-disks list` and `prime-disks delete` make Prime cache disks visible and removable. A cache disk deliberately outlives the pod it was attached to so the next deploy skips re-downloading the weights, which means stopping a deployment halves the spend rather than ending it -- and nothing in the product could see or remove what was left: `delete_disk` existed on the backend and no command reached it, so the only recourse was Prime's web console. Each row carries the disk's size, placement, state and hourly rate, because a listing whose point is the bill should not make the reader look up what it costs -- the placement arrives nested inside the row's `info` block, which a live disk in AP-JP-1 caught. `list` reads the account rather than local state, because local state is dropped on several paths (a create that never became ready, a forgotten entry after a failed attach) and a disk can outlive the record of it; disks Launchpad did not create are listed too, since the point of the command is the bill and a forgotten disk costs the same as a remembered one. Remembered disks the account no longer reports are dropped as they are listed, so the output only ever shows what is billing. `delete` names the disk and its cached weights before destroying them and defaults to no, and a disk Prime still reports as attached is reported as something to retry after the pod's termination propagates rather than as a dead end -- a live cleanup hit exactly that and succeeded seconds later. The retained-disk warning on stop now names this command instead of the web console.
- Endpoints now report what they have actually served: tokens served, live throughput, requests running and queued, KV-cache pressure and average time to first token. Both runtimes already published all of it at `/metrics` and nothing was reading it. The fleet probe now asks there instead of `/health` -- a 2xx from `/metrics` is the same liveness evidence, so the numbers cost no extra requests and, on Modal, wake no container that `/health` was not already waking. A runtime that serves no metrics is remembered rather than re-asked every refresh. Manage shows throughput and total served as columns where the terminal is wide enough and in the selection detail at every width; the home fleet panel carries a one-line summary. llama.cpp on Prime and Vast now starts with `--metrics`, as it already did on Modal, so those endpoints report too after their next deploy. Manage reads traffic for its own rows on a 20s cadence rather than inheriting the home screen's last pass -- the fleet listing is shared across screens and carries no traffic, and the home screen's refresh timer is paused while Manage is up, so the numbers would have sat frozen under a column labelled `tok/s`. The timer stops while the screen is away, and an endpoint that is not in a serving state is never asked, so nothing that had scaled to zero is woken for a reading.
- Token totals survive container restarts. The runtimes only count since their own process started and Modal scales to zero between requests, so the raw counter answers "since this container booted" rather than "since I deployed this". Each reading's contribution is banked as it is observed, using vLLM's process start time to date a restart exactly and falling back to a counter that went backwards where that is not published. Totals persist in `~/.llm_launchpad/serving_usage.json` and stay on a row after it stops; throughput is measured between consecutive refreshes and is left blank rather than invented across a restart or a gap too wide to mean anything.
- Prime cache disks are now sized for the model being deployed instead of a fixed 100 GB. A model whose weights exceed the disk re-downloaded them on every deploy while the disk sat attached and useless; the disk now gets 25% headroom over the planner's weight size (still clamped to the provider's min/max), with the 100 GB floor kept for models with no estimate. Remembered disks too small for the current model are skipped rather than attached, failed disks are forgotten instead of retried first on every future deploy, and location matching ignores separator/case variants (`CANADA-1` vs `canada_1`).
- Fast Deploy now learns each model's memory from llama.cpp instead of only predicting it. The planner reconstructs what ggml will allocate: weights and KV cache from GGUF headers, which is arithmetic on published numbers, and then compute graphs and attention working memory from formulas -- a model of an allocator we do not own, and every correction to it so far has come from a deployment failing rather than from reading the source. llama.cpp computes the true figure before every serve and states it at trace verbosity. That statement is now captured from the deploy log and solved for the two terms a formula cannot derive: the graph memory every device pays in full, and the fixed output and embedding tensors that land on one device. With the shardable part known from the headers, a measurement on any topology determines both, so one deploy sizes every other topology of that model exactly. Calibrations are keyed on the model, context and tuning but deliberately *not* on the GPU -- compute buffers follow tensor shapes, so a measurement taken on two A100s is evidence for three of them, for an RTX PRO placement, and for other providers. They are recorded whether the runtime accepted the plan or refused it; the refusals are the valuable ones, since those are exactly where the formula was wrong, and until now they were discarded. Stored in `~/.llm_launchpad/memory_calibrations.json`.
- Catalog discovery now works to a Hugging Face request budget and remembers which models do and do not have GGUF weights between builds (`~/.llm_launchpad/hf_repo_matches.json`). Matching a benchmark row cost about three requests, a miss cost the most, and misses are the common case because the feed is mostly API-only models -- so every build spent its quota rediscovering that Claude and GPT ship no weights. Both answers are now written down: a resolved repository id for 30 days, a miss for 3, since a model released today may be quantized next week. A build that reaches the ceiling stops, says how many models it did not get to, and is never treated as fresh, so reopening Deploy carries on from where it stopped instead of serving the short list for six hours.
- The main menu's Provider Billing panel reports Vast.ai credit beside Modal workspace spend and the Prime Intellect wallet. Vast bills against credit rather than invoicing, so the number that decides whether a rental can start is the one that was missing. An unconfigured key names `llm-launchpad vast-auth login` instead of reaching the network, and an owed balance is called out separately.
- Vast.ai as a third compute provider, alongside Modal and Prime Intellect: Fast Deploy quotes, GPU filters, and serving-tier competition for verified on-demand NVIDIA offers. Supported llama.cpp GGUF placements on one to eight GPUs can be rented; the endpoint is a loopback SSH tunnel on this computer. Offers a rental cannot actually serve are left out of Fast Deploy rather than listed as unselectable rows. A rented host's GPUs are inventoried over SSH before serving, so a bundle with a different device count, mixed GPU models, or too little free memory per device is refused and destroyed. Stop destroys the rental and its disk.
- vLLM on Vast.ai rentals, on a digest-pinned image whose CUDA floor is read from its own OCI config (13.0, above llama.cpp's 12.8). Tensor parallelism uses every GPU the rental bundles and is limited to counts that can shard attention heads. The API key is passed by environment, never on the command line.
- Image input on Vast.ai rentals through Advanced deploy, on both runtimes. The llama.cpp projector is staged on the rental over the same pinned image Prime uses; vLLM serves images through its native multimodal path. Fast Deploy still refuses vision for every provider, because vision working memory is not calibrated for guaranteed-fit placement.
- `llm-launchpad vast-auth` (login/status/logout), `vast connect`, `offers --provider vast`, and `--provider vast` on deploy/list/status/logs/stop. `doctor` checks for a local Vast key the way it checks Modal and Prime, without authenticating it over the network.
- Advanced deploy can bind a selected Vast rental on either runtime. Disk size is quoted with the GPU.
- Docs for the provider and the broader release plan: `docs/vast.md`, `docs/vast-integration-plan.md`.
- Added an always-on rotating debug log under `~/.llm_launchpad/logs/` and routed previously silent failure paths (cache persistence, auth probing, log-tail cleanup, SSH key permissions) to it.
- Added `llm-launchpad doctor`, a self-check command that verifies the Modal CLI, Modal/Prime/Vast/Hugging Face authentication, that at least one compute provider is usable, the optional Artificial Analysis key, and state-directory writability, with fix hints per failure.
- Added `llm-launchpad --version`.
- Added documentation pages under `docs/` (deploy catalog, Prime provider, storage and costs, OpenCode, troubleshooting) and a generated CLI reference (`docs/cli.md`) via `scripts/generate_cli_reference.py`.
- Added GitHub issue templates for bug reports and feature requests.
- Added `llm-launchpad jobs list/show/follow/cancel` for durable background deployments that survive closing the TUI, with SQLite-backed logs, results, cancellation, and reboot reconciliation.
- Added shared provider readiness (`installed/checking/authenticated/failed`) with async verification; `doctor` now verifies Prime/Vast keys over the network instead of treating stored keys as authenticated.
- Added explicit cost scenarios (Always on, Workday 8h, Sparse, Clustered) with hourly, 24/7, and scenario figures; Modal idle timeout is modeled so sparse vs clustered bills differ.
- Added provider-scoped storage (`Modal/Prime/Vast`) with Prime disk inventory/deletion in the Storage screen and explicit stop consequences (`stop` preview names what survives).

### Changed
- The home screen's Provider Billing panel is one table rather than three stacked sections. Modal, Prime and Vast each had their own heading, their own layout, and their own words for the same four states -- "Refreshing billing report..." against "Refreshing wallet..." against "Refreshing credit...", and three spellings of "could not read that" -- and none of the three said which way the money ran, so a reader could not tell month-to-date spend from a balance that had yet to be drawn down. Every provider is now drawn from one template: its marker and name, its figure in a shared column, then a dim line naming what the figure means (`spent this month`, `balance`, `credit`) and what makes it up. The providers still differ where they genuinely differ; that difference is stated in the row instead of being implied by its shape. Modal gains the unconfigured state Prime and Vast already had, so an unauthenticated workspace names `modal setup` rather than surfacing whatever the CLI said when it was asked anyway. Behind the panel, six message types, three workers and eleven screen attributes became one snapshot type, one fan-out pass and one mapping, and payload parsing moved to `core/provider_billing.py` where something other than a Textual screen can reach it. A fourth provider is now one adapter.
- MTP speculative decoding is now the default on every llama.cpp path instead of a Fast Deploy extra. Deploy-time preflight resolves it from the target GGUF's own NextN heads and the pinned runtime's advertised architectures, so a plain `llm-launchpad deploy` gets it too -- the CLI previously had no way to reach MTP at all, and the same model served through Fast Deploy and through the CLI decoded differently. `--no-mtp` declines it, and that decline now survives preflight rather than being re-decided from the model. Flags a caller wrote itself are left untouched, a certified Fast Deploy placement is never silently given a speculative buffer its memory certificate did not budget, and a model with no MTP heads -- most of them -- is reported plainly instead of as a warning.
- Catalog MTP recommendations are written back to the snapshot the build wrote before them. The probes ran on every launch, resolved which models carried NextN heads, and then discarded the answer: the cached catalog held none, so each start reprobed every repository over 1 MiB range requests and opened the confirm screen with no MTP toggle until they landed.
- Preflight decisions now survive the summarized deploy view. Whether MTP engaged, whether the architecture was verified, and what context and concurrency the endpoint was launched with were all dropped as runtime chatter, so the one line that reports speculative decoding was visible only under `--debug-logs` -- where a reader checking whether MTP was on would never think to look.
- Fast Deploy marks models that can speculate with a `⚡` in the model list, and names it in the detail panel for the selected row. The marker sits in the two-column gutter each row already reserves -- U+26A1 is East Asian Wide, so it measures two cells everywhere and no row shifts out of column. An unmarked row is not a claim that the model cannot speculate: recommendations are attached on a trailing pass, so it means only that nothing has established that it can.
- Hugging Face failures are no longer read as facts about a model. A lookup that errors is recorded as an exclusion instead of being dropped silently, rate limiting is named as itself, and a search whose every probe failed now raises rather than returning "no match" -- an absence of evidence was being written down as evidence of absence, and once persisted it was believed for days. The same applies to weight-size tables: a throttled model page returns nothing, which used to surface as "model size could not be determined" -- a claim about the model rather than about the quota that caused it.
- The Fast Deploy catalog's candidate budget now counts distinct models rather than benchmark rows. Artificial Analysis lists one row per reasoning-effort setting -- Claude Fable 5.1 alone occupies five -- and variants were collapsed only *after* the budget had been spent on them. Candidates whose size the feed does not state share a single pool, and effort variants cluster at the top of the ranking where nearly every model is API-only, so that pool ran out at rank 83 with 67 of its 80 slots held by models that can never have open weights. Deduplicating first extends its reach to rank 145 while examining fewer candidates than before, so it is cheaper as well as more complete. MiniMax-M3, MiMo-V2-Pro, GLM-5, GLM-5.1, Kimi K2.7 Code, Kimi K2.5, DeepSeek V4 Flash and both Inkling builds are now inspected; all are outranked or unsupported, so the shortlist itself is unchanged, but they appear under **x — Excluded models** with a reason instead of being silently absent.
- A Hugging Face lookup that fails is no longer treated as a model that has no weights. Only a genuine no-match leaves a candidate unlisted; an error now records an exclusion, and rate limiting is named as itself. Throttling removes whole stretches of the ranking at once, so a build that lost most of a size category to Hugging Face's quota of 1000 API requests per five minutes published as though it were complete, with nothing on screen to distinguish it from a catalog that had genuinely found nothing.
- Fast Deploy size categories are now measured in total parameters, derived from the published GGUF weight sizes. The benchmark feed carries no parameter field for 436 of its 647 models, so those fell through to a fallback that compared **gigabytes of quantized weights** against thresholds named in **billions of parameters** -- "Compact ≤40B" silently admitted anything up to roughly 71B -- and took the first matching row rather than a representative one. Unsloth's Qwen3.8-Flash-Next page lists a 2.79 GB Q4_K_M beside a 111 GB one, which is how a 177B model came to head the Small category. For a mixture of experts the published weights cover every expert and every expert has to be resident, so this counts the total rather than the active parameters, which is what the category labels claim to mean. The count is the median across every published bit width: size tables carry junk at both ends, and DeepSeek-V4-Flash lists an 11 GB BF16 beside a 155 GB Q4, so no single row can be trusted on its own. The catalog cache version is raised, forcing one rebuild.
- Fast Deploy no longer quotes a catalog price estimate on first open. The estimate prices Modal's published rates at build time, which is rarely what the reader's own providers charge, so every row's number moved under them a second later when live placements answered. The price column now reads `pricing…` until the live snapshot lands. A catalog estimate is still shown when the live load fails or no provider is configured, which is the case where it is the best number available.
- A Fast Deploy tier whose placement another tier already claimed is now named instead of dropped. One placement routinely wins more than one role -- a B200 is often both the fastest and the best tokens-per-dollar, and on the compact models one RTX-PRO-6000 is both the cheapest and the best value -- and the losing label simply disappeared, so six of nine catalog models showed no **Fastest** row at all. The placement still gets one row, because inventing a second would defeat the point of showing the flanks, but it now reads `also the fastest` beside its tradeoff. Being the best value stays unsaid: the recommendation marker already carries it.
- Fast Deploy's serving tiers no longer pick a smaller quantization on the user's behalf. Economy, Balanced and Fastest are now chosen from the best bit width the connected placements can serve, so they differ in price and speed alone. The frontier previously spanned both catalog quantizations, and a smaller one wins every axis the picker ranks -- fewer bytes per weight is both cheaper to hold and faster to read -- so all three tiers landed on 2-bit weights while the model's Artificial Analysis score, measured at full precision, sat on screen beside them. On the compact models both widths place on the same single RTX-PRO-6000, so that trade bought nothing at all. A smaller build is now offered as a fourth **Saver** option only when it is at least 25% cheaper than the 4-bit floor, and always carries its bit width in the row. A model that only fits below the floor -- Kimi K3 is 2-bit or nothing -- is still offered, with the reason stated rather than left to be inferred from the quant label. Four bits is the knee of the quality curve, not a lossless build; lossless remains Q8_0 at best.
- A Vast rental now gets 1800s to answer SSH on either runtime, instead of 900s on llama.cpp and 1800s on vLLM. The old split was scaled on image size, but the pinned images are only 2.59 GB and 8.67 GB compressed — seconds to a minute of download — while the wait is dominated by unpacking them and by Vast's own provisioning, which installs the SSH server the upstream images do not carry. Two of three test hosts exceeded 900s, and the faster links were the ones that failed.
- A rental that stops reporting provisioning progress is handed back early rather than billed out to the deadline, but only where that silence is a measurement. Progress is read from Vast's `status_msg`, ignoring BuildKit's elapsed-time prefix, which keeps ticking while a step is wedged. A host that is running and refusing SSH gets 360s, since the knock is its own signal; one still pulling gets 900s; one that reports nothing at all gets the full deadline and nothing else. Vast leaves `status_msg` empty for stretches of a healthy pull, and a rental measured at 386.6s from creation to SSH sat inside the old 360s window -- so applying that window to an empty status line destroyed hosts that were minutes from serving. A stall report now names the step the host went silent on, which the first one could not.
- A Vast rental's provisioning now shows on the summarized deploy screen while it runs. Nothing a host does before SSH -- the image pull, the unpack, Vast's own sshd install -- matched a summary rule, so a deploy sat on `Renting Vast offer ...` for minutes with no further line and then failed, which reads as a hung client rather than a host still working. Those lines now collapse onto one `Provisioning machine (6m30s)` row that ticks in place, the way Prime's download heartbeat already did, followed by `Machine ready`, the rented GPU inventory and `Server is ready!`.
- A failed operation states its reason once instead of twice. Every operation reports an error and then repeats it verbatim as the completion detail, and the monitor printed both -- a Vast stall message wraps over two lines, so the pair took four of the twelve lines the summary box has. A detail that says something the error did not, such as a cleanup that is still pending, is still shown.
- `doctor` requires one authenticated compute provider rather than all of them, which is what the TUI already gates on. Each provider reports for itself and only warns, and a new **Compute provider** check fails when none is configured. Previously a user deploying happily on Modal still got a failing run and a non-zero exit for not having a Prime key.
- Multi-GPU llama.cpp placements no longer predict faster single-request decoding. The estimate previously assumed roughly 1.6x more decode speed per extra GPU, but llama.cpp splits layers across devices by default, so one request walks them in sequence: extra GPUs buy memory, not speed. **This affects Modal and Prime as well as Vast** -- a multi-GPU placement that previously appeared in the Fastest or Balanced tier on that estimate may now rank lower. Measured attestations are unaffected and still take precedence.
- Deploy forms disable controls their provider ignores and say why, instead of greying them out silently. Vast.ai host/port are fixed by its SSH tunnel, image rebuilds are Modal-only, and llama.cpp cannot pin an HF revision on any marketplace provider.
- Deploy forms and `llm-launchpad deploy` now refuse a configuration its provider cannot run before anything is allocated, rather than failing after the deployment has been routed. Vast.ai previously accepted vLLM, vision, and pinned-revision configurations in the Advanced deploy form and rejected them later.
- Vision option fields keep visible labels, and projector/image details hide when vision is set to text only.

### Changed
- Manage Endpoints opens on what is running. Modal keeps a stopped app listed long after it served anything -- one account's fleet was two rows, both stopped, and the only action either offered was `logs` -- so a screen for *managing* endpoints was mostly a list of things nothing could be done to. Terminal states (stopped, stopping, terminated, archived) are now hidden behind `a`, the way `docker ps` hides them from `docker ps -a`, and the header says how many are waiting there. A `failed` deploy is not filed away with them: a failure is exactly what someone opens Manage to read the logs of. A fleet that is entirely stopped says so rather than reporting an empty fleet, which would invite redeploying something that is merely idle.

### Known issues
- GLM 5.3 Flash at its full 1,048,576-token context does not currently serve on a single B200. llama.cpp aborts in `graph_reserve` asking CUDA for 139,277 MiB (146,042,560,000 bytes) of prompt-processing compute buffers, which is exactly `n_ctx x n_batch x 68` bytes, against a planner estimate of 28 GB for compute and attention scratch combined. Reproduced on five deploys. It is *not* explained: one run on 2026-09-18T01:09Z certified the same model, quant, context, tuning and topology -- 45/45 layers resident, 56.5 tok/s -- from a plan that differs only in `--fit-target`, and retrying with that value produced a byte-identical allocation request and the same failure. The formula was left alone rather than refitted to a single measurement that a successful run contradicts. Nothing is learned from the failure either: the calibration recorder listens for llama.cpp's `--fit` report, which this path never reaches, so each attempt rediscovers it at the cost of a run. Smaller contexts and the multi-GPU placements are unaffected.

### Fixed
- A Modal vLLM endpoint is no longer open to anyone who learns its URL. Prime mints a bearer token before it provisions and Vast mints one before it rents; Modal minted nothing and forwarded nothing, and `modal_vllm_app.py` contained no reference to an API key at all -- so every `*.modal.run` vLLM endpoint this tool has ever published served chat completions, on the account's own GPU and bill, to any unauthenticated caller. This was not a configuration the user could correct: no form field, CLI flag or setting reached `endpoint_api_key` on the Modal path, and the surrounding code treats "Modal without a key" as an ordinary state -- status probes have a dedicated branch for it. The Modal deploy now mints the same `secrets.token_urlsafe(32)` token the other two providers use and passes it as `VLLM_API_KEY`, which vLLM reads itself, so the key never appears in `ps`. A key the caller chose is kept. The connection card, the stored connection summary and the OpenCode sync were already carrying whatever key the config held, so all three start reporting it with no further change. **The Modal llama.cpp path has the same hole and is not fixed here** -- it takes its configuration from a JSON file on the shared volume rather than from the deploy environment, so it needs its own change and its own live run.
- The Advanced vLLM form's VRAM estimate is no longer wrong by an order of magnitude. Three separate errors compounded on one line of text. Hugging Face's `safetensors.total` is a **parameter count**, and it was read as a byte count, so every bf16 model was sized at half its weights; the per-dtype breakdown beside it is now what converts to bytes, which also sizes a mixed-precision checkpoint correctly. The KV cache was computed from the hidden size across every layer, which charges each query head for a cache it shares with its group and charges a recurrent layer for a cache it does not keep -- on a model with 4 KV heads and full attention every fourth layer that is twenty times the real figure. And Hugging Face's expanded `config` is a trimmed view carrying the architecture and the tokenizer but not the shape, which stopped the repository's own `config.json` from being read at all, so a multimodal repo's `text_config` was never found and the model was sized from a guessed transformer. Qwen3.8 27B at its native context read **517.8 GB** against a true ~87 GB; that number is the one Prime and Vast filter their offers by, so both marketplaces showed zero compatible rentals for a model that fits on one 80 GB card. Sliding-window layers are still charged the full context, because overstating a bounded cache is the direction that fits.
- Qwen 3.5 and Qwen 3.8 deployments can call tools, which means OpenCode can talk to them at all. The tool-parser recommendation matched `qwen3-`, and those releases name themselves `Qwen3.5-27B` and `Qwen3.8-27B`, so they fell through to no parser -- and a vLLM server started without `--tool-call-parser` does not merely lack a feature: it rejects `tool_choice: "auto"` outright, which is what OpenCode sends on every request. A live Modal deployment of Qwen3.8 27B served chat and streamed tokens perfectly and then failed OpenCode's first message with `"auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser to be set`. The dotted releases also changed format, so the recommendation is not simply the `hermes` the prefix would have given them: their published chat templates emit `<function=name><parameter=key>`, the XML shape Qwen3-Coder introduced, where Qwen3-8B still emits Hermes JSON -- so they get `qwen3_xml`, read from the templates rather than inferred from the version number.
- A thinking model's reasoning no longer arrives as its answer. The Advanced vLLM form prefills the tool-call parser from the model but had no equivalent for `--reasoning-parser`, so nothing separated `<think>...</think>` from the reply -- while the OpenCode provider Launchpad writes declares `reasoning_content` as the interleaved field whenever the chat template names it. The declaration and the running server disagreed, and OpenCode showed the model's deliberation as the response: a live Modal deployment of Qwen3.8 27B answered a sentinel prompt with its own reasoning, a `</think>`, and then the sentinel. Qwen3, QwQ and the dotted Qwen 3.x releases now prefill `qwen3`; Qwen3-Coder, which does not think, and the embedding/reranking runtimes are left alone. A parser the user typed is still preserved.
- A Prime download says how far it has got. The heartbeat carries the figure -- `runtime container is downloading the model, 46.6 GB so far` -- and the summary rule looked only for a percentage, threw the rest away, and printed `Downloading model` with nothing but an elapsed timer beside it. On a 55.6 GB checkpoint that is twenty minutes of an unchanging row, on the one screen whose job is to say whether anything is still happening; the equivalent Vast rule has always carried its transfer detail through. It now reads `Downloading model — 46.6 GB so far`.
- A Vast rejection says what Vast said. Every non-2xx response became `Vast request failed (HTTP 400).` and nothing else, because the body can echo the request back -- environment and startup script included -- so all of it was withheld unless `LLM_LAUNCHPAD_API_DEBUG=1` was set. But two of its fields are Vast's own words about the refusal rather than a copy of what was sent, and without them the most ordinary failure on a live marketplace is unreadable: renting an offer that someone else took a moment earlier answers `no_such_ask Instance type by id 47550078 is not available`, and the user saw a bare HTTP code. Those two fields are now read (bounded, and only from a JSON object, so a body that is an echo or an HTML error page is still withheld), and a rental that lost the race is reported as exactly that, with the advice to refresh and pick another.
- A Vast runtime that dies during startup reports what killed it. The heartbeat that watches a starting rental reads the last 25 lines of `server.log`, which is right for a progress line every few seconds and useless as a post-mortem: a Python traceback is far longer than that, so vLLM's `RuntimeError: Engine core initialization failed. See root cause above.` was itself the last line captured and the cause it points at had already scrolled out. Two paid rentals died that way with nothing to show for them. The failure path now re-reads a 200-line window once, when the runtime is known to be gone, and falls back to the heartbeat's lines if that read fails. The third rental named its own cause in one line.
- A Prime deploy that cannot get a cache disk now says why. `_create_cache_disk` swallowed every failure into a bare `return None` at five separate points and logged none of them, so a revoked key, an exhausted quota, a disk that never came ready and a region that simply has no disk product all reached the user as the same sentence: "Prime cache disk unavailable; model weights will not persist across deploys". The disk is the thing that stops the next deploy re-downloading the weights -- 55.6 GB and eight minutes on the run that surfaced this -- so an unexplained "unavailable" is an unactionable recurring bill. Each path now records its reason, the message carries it, and the exception reaches the debug log the way the other silent paths already do.
- The test suite no longer writes the developer's own OpenCode configuration. Seven `CliMainCommandTests` cases drive `deploy` and `switch` through the real CLI without stubbing the sync, so every run rewrote `~/.config/opencode/opencode.json` -- and one of them had, at some point, left a provider in it pointing at `https://alice--llamacpp-org-model-gguf-serve.modal.run`, a fixture host, carried forward unchanged by each subsequent run. - A synced OpenCode provider carries the endpoint's API key again. The key is minted during the deploy, on the config the lifecycle executes -- which is rebuilt from the resolved plan and is *not* the object the caller kept a handle to -- and callers sync OpenCode from their own config. The key therefore never travelled back, and the provider was written with a `baseURL` and no `apiKey`: OpenCode answered `401 Invalid API Key` against an endpoint that had deployed, certified and was serving correctly, and the only way out was a later `opencode sync`, which recovers the key from the connection store. - The placement a deploy was certified on now reaches the runtime that serves it. Every execution path resolves its config into a `ResolvedDeploymentPlan` first, and the lifecycle then assigns that plan's `runtime_tuning` and `placement_assessment` onto the config unconditionally -- but the plan is built from a `DeploymentRequest`, which carries intent rather than evidence and has no field for either. Both were therefore resolved as `None` and *erased* what Fast Deploy had already certified: runtime certification failed outright with "No placement assessment was supplied for runtime certification" after a full deploy and download, and the endpoint was served with a tuning re-derived from the serving objective instead of the certified one, silently substituting the 2 GiB default runtime margin for the device-sized one. Preflight now passes a caller's resolved tuning, assessment, reasoning and vision straight through, so the plan records what will actually be executed. A config that resolved none of it still plans exactly as before.
- The GGUF staging downloader actually runs on Prime and Vast. It was invoked as `python3 - <args> <program>`, and `python3 -` reads the program from *standard input* -- which under `nohup … < /dev/null` is empty. The interpreter therefore ran nothing, exited 0, and left the real program sitting in argv, so every rental staged no weights and wrote no `weights.args`, while the comment above the call asserted the opposite ("python reads argv, never stdin"). llama.cpp was then handed an empty `--hf-file` and reported `failed to load model ''`: a sentence about the model, for a downloader that had never run. The program is now passed to `-c` with its arguments after it. Every test here checked the *text* of the command; one now runs the prelude against a real interpreter with the Hub stubbed and asserts the staged file name is on disk. The Vast startup script also announces itself on its first line, so an empty `server.log` means the script has not started rather than that it died without a word -- which is the distinction the startup watcher has to make before calling a rental dead.
- Fast Deploy sizes llama.cpp's runtime margin from the GPU it picked, not from the catalog's floor. `compile_server_args` has always promised that "the topology-specific compiler raises this margin to 5% on larger accelerators", and only the retune path -- taken when the serving objective is changed on the confirm screen -- ever kept it. A deploy accepted as offered inherited the catalog's 2 GiB floor, which is what the catalog itself must use because it is built before any GPU is chosen, so the same placement was served with a 2 GiB margin or a 9 GiB one depending on whether the user had touched an unrelated dropdown. The margin is now applied where the device becomes known, on the Modal/Prime placement path and the Vast offer path alike, and the plan carries the arguments it was assessed under. It is deliberately not part of the calibration key, so a re-cut recipe still matches measurements taken on any other topology of the same plan. This does **not** resolve the GLM-5.3-Flash `graph_reserve` failure noted under Known issues: that placement was retried with the 9 GiB margin and requested the identical 139,277 MiB.
- The staged GGUF's file name reaches llama.cpp again on Prime and Vast. Both providers wrote `$(cat .../weights.args)` into the argument list and then joined it with `shlex.join`, which quotes every argument -- that is what it is for -- so no command substitution ever ran and the server was started with that text as its file name. llama.cpp resolved the nonsense against the repo listing and reported `failed to load model ''`, which reads as a bad model rather than as a bad command line and cost a rental per diagnosis. The name is now read into a shell variable before the exec and referenced as one quoted word, so a shard path containing a space stays a single argument, and an empty `weights.args` is refused by name instead of passed on as `''`. Both providers build that line through one helper, which is exercised by running it in a real shell against a stub server that records the argv it was handed.
- llama.cpp weights stage again on Prime and Vast. The shared prelude exports the Hugging Face download settings before handing the repository, quant and cache paths to the staging interpreter, and those exports were joined on a bare space rather than the `; ` every other line in the block uses. A POSIX shell reads that as one `export` command taking the next `export`, then `python3` and its `-`, as variable names, so under `set -eu` every rental died on `export: -: bad variable name` in its first second, before a byte was staged. The existing tests asserted on substrings of the generated script, which cannot see statement boundaries and passed throughout; the prelude is now executed in a real shell against a stub interpreter that records the argv and environment it was actually handed.
- A Vast rental whose runtime exits is reported now, with the reason it printed, instead of at the deadline. The startup watcher read only the server log, and a script that has exited leaves a log that simply stops changing -- indistinguishable from a slow download -- so a host whose runtime died immediately billed for the full 30-minute allowance and then reported "startup timed out or its SSH tunnel disconnected", while the real message sat unread in `server.log` the whole time. The startup probe now also reports whether any runtime process is still on the host, and a positive "nothing running" reading with an endpoint that is still not answering ends the deploy with the log's last line. Absence needs corroboration before it means an exit: "no process and nothing logged" is also what the seconds before the script starts look like, and acting on that destroyed a healthy rental 74s into a deploy, so the runtime has to have left a trace -- something in its log, or an earlier probe that saw it running -- first. A probe that could not answer at all is a busy host, not a dead one. The model-startup deadlines are named constants rather than inline literals, so a regression that stops watching fails a test in seconds instead of spinning out the half hour.
- A Hugging Face rate limit no longer replaces the model catalog with a worse one and calls it live. Discovery walks down the Artificial Analysis ranking until each size category is full, so throttling that removes the *top* of the list is answered by filling the categories from far below it. An observed rebuild lost every model ranked above 390 to HTTP 429 -- GLM-5.3, Kimi K3, GLM 5.3 Flash, Qwen3.8 27B -- back-filled with DeepSeek V3, Grok 2 and Apertus 70B, and published 335 profiles over a cached 167. The retention guard compared profile *counts*, so twice as many models read as an improvement and the good snapshot was overwritten. Whether a rebuild is worse is now decided on which models it could not check rather than on how many survived: an exclusion records whether the build reached a conclusion or merely failed to look, and a rebuild that leaves a model unchecked which the previous catalog had already resolved keeps the previous catalog and says which models it could not reach. The same flag fixes two more readers that each matched one reason string: freshness treated a catalog gutted by HTTP 429 as fresh for the whole six-hour TTL, because only the exhausted-request-budget wording counted as incomplete, and Deploy's "N models not yet checked" line stayed silent for the same reason. The catalog cache schema is bumped, so an older snapshot is rebuilt rather than read as complete.
- Fast Deploy no longer claims a superlative the row below it disproves. The placement frontier is drawn at one bit width, so "the fastest" means the fastest at that width -- but the Saver row is rendered in the same list, and a reader compares rows, not partitions. GLM 5.3 Flash shipped a recommended row reading "also the fastest" at ~12 tok/s directly above a Saver row reading "~30 tok/s · 2.5x faster". The claim is now narrowed to the quality it was decided within ("also the fastest at 8-bit") whenever the Saver row beats it on that axis, which keeps the reason the clause exists -- stopping the reader going off to the full placement list after something that is not there -- without asserting something the screen contradicts.
- A Vast rental Vast itself refused no longer blocks its own deployment name forever. Offers race away between pricing and acceptance, and Vast answers the rental with HTTP 400; the recovery record written before that billable request then had no instance id, so cleanup reconciled by label, found zero instances, and reported "rental creation remains uncertain". The record survived, and the name was refused from both sides -- deploy called it "already recorded", destroy called it "uncertain" -- with no way out through the product. A 4xx other than 429 is the provider stating it did not act, so nothing exists under that label and the record is dropped; a timeout, a 5xx or a transport error still keep it, because Vast may act moments after the reply was lost.
- A deployment is no longer destroyed because the provider's log stream lost a line. Runtime certification reads GPU residency off llama.cpp's own offload report, and when that report was absent it failed the endpoint and tore it down. Three GLM-5.3-Flash deploys (UD-Q2_K_XL, 1,048,576 tokens, one B200) were killed that way tonight after the server had loaded, answered `/props` and served a completion: Modal's log stream had a ~70-second hole across the whole tensor-load phase -- llama.cpp's own clock jumps from 0.01.647 straight to 1.11.582, and the provider's retained logs show the same gap, so nothing local could have recovered it -- and that window is exactly where the offload report is printed, immediately after llama.cpp emits some two hundred unused-tensor warnings in one millisecond. Evidence that *contradicts* residency still fails the endpoint, and now says what it saw (`reported 30/32 layers on GPU`). Evidence that is merely missing no longer does: the retained logs are re-read, then the certificate for this same placement fingerprint is consulted -- an earlier run of the identical model, context, tuning and shape is an observation, made then rather than now -- and only after both come back empty is residency called unknown. The endpoint then keeps serving and its certificate records `residency_evidence: predicted`, so a prediction is stored as a prediction instead of being laundered into a measurement or used to justify a teardown. Certificates written before this field read as ungraded rather than as verified. Confirmed by redeploying the exact configuration that had just failed three times: certified in 88s at the full 1,048,576-token context, 45/45 layers, 56.5 tok/s single and 34.9 aggregate.
- A Hugging Face model page that could not be read is no longer recorded as a model with no weights. Per-quant weight sizes have exactly one source -- the model page's own quantization table, scraped as HTML, because the Hub API lists the GGUF files but not their sizes -- and the scraper returned nothing for every failure alike: a 429, a timeout, a dropped connection, any non-2xx. An empty table then read downstream as "No GGUF quantization has a usable weight-size estimate" or "Model size could not be determined from the available metadata", both claims about the model, and the model left Fast Deploy until the next rebuild six hours later. The 2026-09-18 build excluded 38 of 40 models on those two lines, among them Qwen3.8 27B at rank 63 -- the top-ranked Compact candidate, which the category then filled from three models ranked below it -- and every one of them sizes cleanly on a retry. An unreadable page now raises, so the three-attempt backoff already wrapped around this lookup actually covers it and the exclusion names Hugging Face rather than the model; the failure is written to the debug log, which previously held no trace of it. A degraded reading is no longer cached: one throttled request used to answer for that repository for the whole cache window, including the retries meant to recover from it. A page failure where the API does carry sizes stays harmless, and callers that only want the architecture -- deploy preflight among them -- still get their metadata, now with `weight_size_error` set rather than an empty table presented as the answer.
- A mixture-of-experts repository is no longer sized by one of its experts. When neither the model config nor the safetensors index states a parameter count, the count is read off the repository id -- and that reader took the second number in "Mixtral-8x7B", calling a 47B model a 7B one, and "Mixtral-8x22B" a 22B one. The benchmark feed's own parser has always understood the experts-by-size form; only the repository-id fallback did not, so the two disagreed by a factor of eight on the best-known MoE family and the VRAM estimate built on it came out six times too small. The product is used instead, which slightly overshoots the true total because experts share attention and embeddings -- the direction that still fits the card.
- Ternary quantizations are recognised as the reduced quality they are. Bit width is read from the label, and the pattern knew llama.cpp's importance-matrix prefix but not its ternary one, so `TQ1_0` -- about 1.69 bits per weight, the lowest tier that exists -- parsed as nothing at all. An unparsed label is deliberately scored at the 4-bit quality floor, so that a format nobody has taught the ranker about is not buried; the effect here was that a ternary build ranked level with `Q4_K_M`, sat in the primary tier rather than behind the Saver disclosure, and was presented without the bit width beside it. That is exactly the silent degradation the quality axis was added to prevent.
- Fast Deploy no longer claims its placements are sorted by a price. The list is ordered on each placement's assessment, which the status line already describes as "best full-context throughput first"; a second line three rows below asserted they were "sorted by 'Workday 8h' scenario cost". Both cannot be true, and the rows visibly disagreed with the one that named a price -- a scale-to-zero placement showing $360/mo sat above a provisioned one showing $240/mo, because the ordering used a different monthly basis again from the figure on the row. The scenario behind the per-row figure is still named, since the number means nothing without its assumptions; the claim about ordering is gone, along with the helper whose stated contract was to describe an ordering no list has.
- Cancelling a background deployment now stops what it started on Modal and Vast. The worker would only tear a resource down once it had seen an allocation event, and Modal never emits one -- its app is addressed by name, not by an id -- so cancelling a Modal deploy skipped the teardown entirely and told the reader "Cancelled before allocating a resource" while the app stayed published. The TUI's own in-session path has always stopped by name; only the durable worker, which is the path almost every deploy now takes, diverged. Vast was in the same position, since its destroy resolves the rental from the record it persisted under the deployment's name. Prime keeps its requirement of a pod id, because Prime genuinely cannot terminate without one and emits it the moment the pod exists -- so for Prime, no id really does mean no pod.
- A cancellation during warmup no longer strands the pod the deploy allocated. The warmup path passed whatever endpoint object it happened to be holding, which carries no `app_id` when the pod arrived as a bare allocation event, so the id the deploy phase had already banked in the job store was thrown away and a live Prime pod was left billing. The id is re-read from the job when the caller has none.
- Cancellation logs say which wait was interrupted. Every call site passed a distinct phrase -- cancelled before the placement started, during provisioning, during warmup -- and the parameter carrying it was accepted and never used, so all three cancellations read identically and the log jumped straight from the last provider line to a verdict.
- Background deployments record their startup-phase timings. Moving deploys into a detached worker made it the path almost every TUI deploy takes, and it was the one path that never built a phase timer: `startup-phase deploy/warmup-wait/total` lines appeared for the headless CLI and for the in-session fallback, and not for the deploys people actually run.
- A provider that never answers no longer holds the app open at exit. Fast Deploy's availability fetch gives the three providers a shared 45s budget and then reports whichever did not arrive, and the pool it ran on was deliberately not used as a context manager so a slow fetch would be "abandoned". It was not: a `ThreadPoolExecutor`'s workers are joined by the interpreter at exit whatever `shutdown()` is told, so the unbounded wait was not removed but deferred to quitting time, where it holds the process open with no interface left to explain the delay -- measured at eight seconds for an eight-second fetch. The fetches now run on daemon threads, which are genuinely dropped; each still has its own request timeout underneath.
- An installed Modal CLI is no longer mistaken for a Modal credential. The readiness module exists to keep installation, credential presence and verified access apart, and its own unverified path collapsed the first two: a CLI on `PATH` reported "credentials present" without reading any auth state, so `has_provider_credentials` -- documented as the setup gate, with "installation alone is not enough for Modal" written into it -- returned true for a Modal that had never been authenticated. The unverified check now reads Modal's local auth state, as the Prime and Vast checks already read their stored keys.
- The fleet panel no longer says "checked 12m ago ago". `format_age` already ends in "ago" (or reads "just now"), and the sentence around it supplied a second one, so every passively monitored Modal row carried the duplicate -- and "checked just now ago" on top of it.
- Token counts shed their digits at every decade now, including the first. The formatter promotes a count that only rounds up into the next unit, so 999,999 reads as `1.0M` rather than `1,000K`, but the `< 1000` guard short-circuited ahead of that rule and 999.6 printed as `1,000`: five characters in a column sized for four, and the one decade that failed to follow the formatter's own promise. Throughput handed over at the same boundary, so an endpoint at 999.6 tok/s read `1,000 tok/s` beside neighbours reading `1.0K tok/s`.
- A physical batch that already fits the attention-scratch budget is left at the size it was asked for. The ladder the planner steps a batch *down* to was also imposed as a ceiling, so a caller configuring 2048 was silently cut to 512 on the strength of a scratch cost of nearly nothing -- while a cost of exactly nothing returned 2048 untouched, the same request answered two different ways either side of zero.
- `LLAMACPP_HYDRATION_MODE=""` selects the documented skip mode. `os.environ.get(..., "marker").strip().casefold() or "marker"` folded an explicit empty value back into the default, so the branch that reads it was unreachable and the validation error went on offering `'marker'`, `'always'`, or empty (skip) -- one of which could never be set. An unset variable still takes the default.
- A Prime cache disk is reused only at the size a new one would be created at. Creation gives 25% headroom over the planner's weight size, for HF bookkeeping and quant rotation, but reuse compared against the bare weight figure: a 100 GB disk was accepted for 99 GB of weights that a fresh disk would have been given 124 GB for, so the download filled the disk the headroom exists to prevent filling. Both sides now ask the same function.
- Listing Prime disks reads every page. The pagination stopped as soon as `offset` reached a total the account may not report, so an account whose response carries no `total_count` returned only its first 100 disks -- and the caller then forgets the local record of every disk the listing omits, which is exactly how a disk outlives the record of it and keeps billing with nothing naming it. A `total_count` of `null` crashed the listing outright on `int(None)`. Paging now ends on a short page, and an unreadable total is treated as unknown rather than as zero.
- A deployment worker that stops reporting is flagged. `reconcile_workers` documented "a live pid is trusted but flagged" and computed the staleness it needed, then acted only on dead pids: a worker wedged inside a provider call kept its job listed as running indefinitely, and a wedged call bills exactly like a working one. A live worker past the heartbeat timeout now says so in its outcome without being ended -- only the worker may end its own job -- while a job that was never claimed stays pending for inspection rather than being called stalled.
- The Operations screen no longer runs job reconciliation on its repaint timer. Reconciling reads every active job out of SQLite, adopts legacy journal entries and writes as it goes; it was on the 0.5s refresh, so opening the screen put those transactions on the event loop twice a second for as long as it stayed open. Repaints now read; reconciliation keeps its own 10s cadence and still runs once on mount.
- A Fast Deploy search that matches nothing says so, instead of reporting an empty catalog. "No models in the quick-deploy catalog" sent a reader whose search term simply missed off to rebuild a catalog that was fine. The GPU filter and the top-ten view still explain the absences a search term cannot.
- The Fast Deploy search box can be put away again. On a constrained terminal it is a temporary control that borrows rows from the model list, revealed by `/` and hidden otherwise -- but nothing ever cleared `search-open` except leaving step one and coming back, so a single press shortened the model list for the rest of the step. Submitting an empty search now gives the rows back; a search with a term in it stays open.
- A failed Prime runtime now reports why it died instead of what it printed last. The restart-loop and exited-container paths took the final line of the container log tail, but a restarting container's tail ends with the *next* attempt's opening lines -- so a live H200 deploy of a 27B model reported its cause of death as `warn: LLAMA_ARG_HOST environment variable is set, but will be overwritten by command line argument --host`, a harmless note llama.cpp prints on every start. The real cause, `get_repo_commit: error: HTTPLIB failed: Could not establish connection` after the container could not reach huggingface.co mid download, sat a few lines above and never reached the user. The detail is now the *first* line that reads like a failure, since the first error is the cause and the rest are its consequences -- the same tail also ended in `failed to load model`, which is only what happens once the download it depended on has already failed -- and llama.cpp's own W-level and `warn:` lines are never eligible.
- Stopping a Prime deployment now says what it did not stop. Terminating the pod deliberately keeps the managed cache disk so the next deploy skips re-downloading the weights, but that disk goes on billing with no pod to show for it and nothing reported it: the stop said only "Terminated Prime pod", while the Vast path spells out that stopping destroys its disk and model cache. A live 27B deploy left a 100 GB disk behind this way, and the disk could not even be deleted until the pod's termination had propagated (`Disk is attached to resources`). Each retained disk is now named on stop with its size and location and the fact that it keeps billing, carried through the summary view in full rather than collapsed, since the disk's identity is the actionable part. Reporting never fails a teardown. Note that nothing in the product deletes these disks yet -- `delete_disk` exists on the backend but no CLI or screen reaches it -- so the message points at the Prime console.
- Fast Deploy can no longer hang on "loading" because one provider stopped answering. The Modal, Prime and Vast catalogs are fetched concurrently and were then awaited with `future.result()` and no timeout, so a single stalled fetch had no deadline and no way back: the screen offers nothing to return to and the phase never advances. The three fetches now share a 45s budget: whatever has not arrived is reported as that provider's own error and the providers that did answer are still shown, because availability is a comparison across providers and a slow one should cost its own row rather than the whole screen. The thread pool is no longer used as a context manager either, since its exit joins every worker and would have restored the unbounded wait the budget exists to remove.
- A Vast rental that is still installing its SSH server is no longer destroyed for it. The stall window for the SSH wait was 360s, set to the only measurement available at the time -- and that measurement was the healthy case, not the wedge: the fastest success on record answered SSH 386.6s after creation, so the window closed on the population it was meant to protect. A live RTX PRO 6000 rental was destroyed after 378s of refusals while it was still working, and the retry it forced cost a second rental and another eight minutes. The window is now 900s, clear of every success on record and still handing a genuinely wedged host back at half the deadline, and it is timed from the first knock rather than from the last status change -- Vast freezes `status_msg` at `success, running <image>` when the pull finishes and never writes another line, so the old clock was charging sshd for however long the pull happened to take. A denied key, which is the case the window was really aimed at, is now told apart from a refused port and ends the rental well inside that window instead of waiting it out -- but only once the host has had 150s to install the key Vast attaches asynchronously, because failing on the first denial destroyed a healthy RTX PRO 6000 WS rental 49.7s into its deploy, one second after the host came up. An SSH authentication-attempt limit is classified as neither, because it is a verdict on how often this loop knocked rather than on the key it offered -- the deploy path already notes that hundreds of failed authentications look like an attack to Vast's shared proxy, so reading the limit that provokes as a rejected key blames the rental for our own polling; the knock backs off to its maximum instead. A changed host key is classified as neither either: the rental is reached through a shared proxy that answers before the container's own sshd, so the key seen in the first seconds is not always the one the rental settles on, and reading that churn as an authentication decision ends a working host in seconds. OpenSSH's stderr is still never echoed without `LLM_LAUNCHPAD_SSH_DEBUG=1`. While a host is refusing, the log says it is installing its SSH server rather than advising the reader to check their saved host key.
- A Vast deploy now says what it is doing while the weights arrive. The rental loop heartbeats every 30s and then stopped: the model download and load, which is the longest stretch of the deploy and can run tens of GB, reported nothing at all, leaving `Rented GPUs` as the last line on screen for ten minutes of healthy work. llama.cpp draws its download as a carriage-returned progress bar that a redirected log never receives, so the server log holds one stale line for the whole download and tailing it showed nothing either. The wait now reports on the same 30s cadence from the partial weight files on disk -- `.downloadInProgress` for llama.cpp, `.incomplete` for the Hugging Face hub -- naming the gigabytes fetched and the rate they are arriving at, and falling back to the server log once the weights have landed and it has loading and warmup to report. The probe rides the SSH tunnel the deploy already opened rather than dialling Vast's shared proxy once per heartbeat, and a host too busy to answer it is reported as still starting rather than ending a rental that is already billing. In the summary view the heartbeat collapses onto one ticking `Downloading model` row.
- The fleet no longer lists an endpoint called "default" that nobody deployed. `modal run` creates an app for the duration of the call, and two helper entrypoints -- the storage screen's model listing and the predownload -- passed no environment, so the app took the backend script's fallback name. That fallback is `llamacpp-server`, the pre-instance app name, which discovery reads as a real llama.cpp deployment whose instance is `default`. One account had thirteen of them, each alive for seven seconds, collapsed by the deduplicator into a single convincing row. Helper runs are now named `llp-util-<backend>`, which no discovery pattern claims, so they stay out of the fleet instead of being filtered back out of it.
- A stopped Modal app no longer advertises a Base URL. A row the provider gives no web URL for had one synthesized from the username and app name, which is right for an app still starting and a fabrication for one that is over -- the phantom `default` row offered a copyable endpoint that had never served a request and would only ever hang. A URL the provider actually reports is still shown whatever the state. The home panel is unaffected: it has always hidden stopped apps, so only Manage Endpoints ever displayed one.
- The memory estimate now counts a sparse-attention model's mask planes, which it was missing entirely. GLM's indexer builds its top-k mask by duplicating, scattering into and adding masks shaped `[context x physical batch]`, and those intermediates exist whether or not flash attention is on. A live 2x A100-80GB fit measured 14.7 GiB of compute buffers per device where the plain heuristic -- capped at 16 GB and independent of context -- predicted 8.8 GiB. Counting the five intermediates from `build_attn_sparse` plus the base mask puts the estimate at 14.6 GiB. Every attention implementation also reserves at least that base mask, f16 under flash attention and f32 without it, so long-context plans of any architecture are sized a little more honestly.
- A multi-GPU plan is now sized on its busiest device rather than the average. llama.cpp assigns whole layers, so 45 layers over two GPUs is 23 and 22 -- a 51/49 split. A measured GLM-5.3-Flash plan put 78,810 MiB on CUDA0 against 74,738 MiB on CUDA1 and was refused for a 433 MiB shortfall while the pair together had 7.8 GB to spare: perfectly even halves would have fit, and llama.cpp cannot split a layer. `per_device_required_gb` now carries the real per-device figures instead of the same average repeated, and the two topology pickers size on the largest of them.
- A deploy with two things happening at once no longer looks finished while one is still running. The summary spinner was chosen by taking the last step-or-done row and marking it only if it was a step, which assumes the two alternate. A Prime deploy polls the tunnel and the runtime together, so `Secure endpoint connected` arrives while the container image is still being built: the spinner disappeared, every row took a tick, and a build with twenty minutes left to run read as a completed deploy. The last step is now the one marked, for as long as the operation is running.
- A Prime source build is no longer reported as `Pulling container image`. GLM-5.3-Flash's runtime is compiled on the pod from a pinned llama.cpp revision with CUDA, which takes far longer than a pull, and the status probe called every pre-container state "pulling the runtime image" -- so a long compile looked like a stalled download with nothing to distinguish the two. The probe now reports `Building container image (N%)`, taking cmake's own percentage out of the bootstrap log. It reads the exit status, the image kind and the build log in the same round trip the status check already made, so a pod that is busy compiling does not get a second SSH connection every five seconds.
- The Prime model-download counter never actually counted. The byte total was measured with `du ... | awk "{s+=$1} ..."` inside `docker exec sh -lc '...'`, where the container's shell expanded `$1` to nothing before awk saw it; awk exited on a syntax error, `CACHE:` came back empty on every poll, and the percentage silently fell back to docker's network counter. It now totals with `du -c`, which needs no `$` and survives both shells.
- A Prime model download reports what it has fetched even when no size is known. With a planner weight estimate the line carries the percentage and the figures behind it (`downloading the model (38%), 42.1 of 109.0 GB`); without one it reports bytes so far, but only once two polls show the count still moving -- the network counter holds its final value while weights load into VRAM, so treating any traffic as a download would pin the step at "downloading" forever.
- GLM-5.3-Flash is no longer planned with flash attention off, which is what made it undeployable. The pinned runtime was recorded as requiring it off; nothing in llama.cpp asks for that. The revision the image builds *extends* flash attention for this model, adding `ggml_flash_attn_ext_set_n_kv_max` so its sparse top-k path can use the kernel and casting the top-k mask to f16 for it, and `glm5next.cpp` contains no guard against it. Turning it off costs an enormous amount: without flash attention llama.cpp materializes the attention scores, `[context x physical batch x query heads]` in f32 plus an f32 mask, reserved at the worst case -- for this model's million-token window, **140 GB on every GPU**, more than the weights. So a 2x A100-80GB plan was published at an estimated 139.5 GB against 160 GB of VRAM, cached 109 GB of weights, started the container, and only then had the plan rejected by llama.cpp's own memory planner. The 4-bit build is back on 3x RTX-PRO-6000 or 2x B200 and the 2-bit build on a single B200. An f16 KV cache is still pinned for the architecture, and TF32 stays off in the image; only the flash-attention claim was wrong. Generation quality on this unmerged runtime remains unverified, so if output degrades, that one line is the thing to put back.
- Attention scratch is now part of the memory estimate, so a plan without flash attention is sized on what it actually needs. Compute buffers were a heuristic capped at 16 GB and independent of context, which is why a 140 GB per-device requirement could go unnoticed. When a plan does run without flash attention the planner now also trades the physical batch down (512 to a floor of 64) to keep that buffer within a 16 GB budget, rather than buying GPUs to hold a buffer none of them can share. No catalog model plans that way today; it is the guard that stops the next one being mis-sized in silence.
- Compute-graph memory is no longer divided across the GPUs of a placement. Weights and KV cache shard; the graph does not, because each device builds its own. A per-device requirement was computed as `total / gpu_count` for every term, so adding a GPU appeared to shrink buffers that are in fact replicated. The two places that sized a topology -- the catalog's shape picker and the live placement matcher -- now share one rule with the assessment they feed, which also stops a model from being dropped entirely because the matcher proposed a topology the assessment then rejected.
- A serving plan llama.cpp rejects is now reported as the memory shortfall it is. The runtime aborts its fit at whichever guard it reaches first, which for a GPU-only plan is always the explicit `--n-gpu-layers` -- it only gets that far after finding it cannot meet the free-memory margin and cannot shrink a context the caller pinned. The deploy log showed `n_gpu_layers already set by user to -2, abort`, which reads like a bad argument rather than a placement that is too small. The pre-flight check now runs the planner at trace verbosity, so its own arithmetic (`projected to use N MiB ... vs. M MiB of free device memory`) reaches the log instead of being filtered out as runtime chatter, and the failure quotes those numbers ahead of llama.cpp's abort text.
- Warmup stops as soon as a container reports a startup failure that will repeat. A plan the hardware cannot hold is rejected identically on every restart, so Modal restarting the crashed container just replayed the same traceback while the readiness probe waited out its full 30-minute budget. That rejection now ends the operation with llama.cpp's verdict as the message, instead of `Timed out after 1800s`.
- The Prime pod-provisioning wait now reports on an interval too. It had the same shape as the runtime wait: a state line only when the state text changed, and a pod can sit in one state for many minutes of a thirty-minute budget. A new test classifies every poll-until-ready loop in `core` as either reporting progress or short enough to stay silent, and drives the reporting ones against a fake clock, so the next provider cannot add a silent one without saying so.
- Prime model-download percentages are now measured against the weights, not the whole serving plan. The expected size written to the pod came from `required_vram_gb`, which is weights plus KV cache plus compute buffers plus reserve -- roughly a third larger than anything the pod downloads. A finished 109 GB download therefore read as about 75%, and because completion is detected at 98% of the expected size it never read as finished at all: the step sat at three quarters for the entire model load. The planner already records the weight size, so that is what gets used; when no planner estimate exists the deploy reports elapsed time instead of a percentage that cannot reach its own end.
- A Prime deployment now reports that it is still working every 30 seconds while the model downloads. Runtime lines were emitted only when their detail text changed, and the detail is a constant string whenever the pod cannot report an expected download size -- so a 109 GB model produced one log line and then minutes of silence on a screen that bills by the hour. Vast already reported at this cadence while a host provisions. The waiting step now carries how long it has been waiting (`Loading model (5m20s)`) and replaces itself in place rather than stacking up a row per update; a step that has a real percentage keeps the percentage instead, since that already shows movement.
- Up and down now move between the controls on the confirm-and-deploy and Settings screens. Textual moves focus with tab, which is close to unusable on a phone where tab is an item in a modifier bar. Worse, a closed `Select` binds "down" to opening its own overlay, so arrowing down from the fulfillment dropdown went *into* the list and every further press moved within it -- the Deploy button was unreachable by arrow at all. Settings had no arrow navigation whatever: focus started in an input and the keys moved nothing, which mattered most because that is where mouse support is switched on when taps are being ignored. An open dropdown still keeps the arrows, since that is how one of its options gets chosen.
- Settings no longer reports mouse support as on when it is off. The switch defaulted to a flat `True` whenever the preference had never been set, but an unset preference resolves to *off* over SSH so the terminal keeps its own text selection -- so an SSH user who went looking for why clicks did nothing was told clicks were enabled. It now shows the state the app actually resolved, and setting it persists.
- The deploy hint on step 3 no longer runs off the side of a phone terminal, and names `ctrl+t` when taps are disabled. At around 50 columns the full sentence lost its last word, and the footer that would otherwise carry this is hidden behind the on-screen keyboard. Mouse reporting being off means a tap never reaches the app at all, so it cannot report one it never received: the way to enable taps has to be on screen before one is tried.
- The footer now says whether mouse mode is on or off, rather than only naming the toggle. Mouse reporting defaults off over SSH so the terminal keeps its own text selection, which means taps do nothing until `ctrl+t` turns it on -- and a hint reading only `Mouse` could not tell anyone that. On a phone client like Termius, where tapping a button is the obvious thing to try, the Deploy button on step 3 read as unreachable when it was simply not accepting taps. It now reads `^t Mouse off`, and updates when toggled.
- Step 3 of Fast Deploy now states how to deploy from the keyboard, beside the Deploy button. Enter is deliberately not bound there, so a keystroke carried over from step 2 cannot rent a GPU, and the route was named only in the footer -- which the fulfillment dropdown paints over while it is open, exactly when someone is looking for how to continue. On a placement with alternatives, which is most Vast.ai ones, focus starts on that dropdown, so enter opened it, enter chose an entry, and the next enter reopened it: a loop with no visible way forward.
- A background storage refresh overwrote text being typed into the pre-download form. Repopulating the table moves its cursor, Textual reports that as a row highlight exactly like a keypress would, and the highlight handler prefills the form: half-typed "Qwen" became the highlighted row's full model id, on a timer, mid-word. A refresh now leaves an edited form alone, while the first snapshot still prefills and moving to another row still prefills.
- Every form screen had a tab stop where nothing appeared focused. Textual makes scroll regions focusable so a keyboard user can scroll a region with nothing in it to focus, which a form is not; those regions are now out of the tab cycle, and Settings opens on its first field instead of on its scrollbar.
- A failed operation left the status bar reading `state: idle` or `state: deploying` on a screen whose only other line said it had failed. `DeploymentState` has no failed member, so the state the deployment reached is kept and the failure is now said alongside it.
- The home screen's Deployment Status panel was capped at 14 rows and scrolled its own content while the rows directly beneath it stayed blank. Two deployments were already enough to clip an entry mid-endpoint with ten unused rows underneath. The panel now takes the column height that billing does not.
- A home menu row wrapped mid-phrase, orphaning "delete" on a line of its own, on a 120-column terminal. The label breakpoints measured the terminal, but the list only gets what the status column leaves of a layout capped at 126. Labels are now chosen against the width the list actually receives, and a compact terminal keeps its concise names rather than being talked back up into a padded grid.
- The setup screen opened scrolled past its own title. It focuses the Re-check button on mount, and Textual scrolled that button into view, so the screen whose entire job is explaining how to authenticate showed neither its heading nor the first two of its three options on a short terminal.
- Deploy's model picker said the same two things two or three times: the title, subtitle and status line between them repeated "Pick a model" and the catalog's source label. The subtitle now carries the provenance and the status line the counts. Its search box was also unlabelled beside a labelled GPU filter, and both were capped at 36 columns, leaving the row more than half empty on a wide terminal while model names below were still being truncated.
- Deploy's model list printed "unranked" on every row when no Artificial Analysis key is configured, which is every row of the list saying nothing. A model with no score now shows no score; the detail panel still names it for the selected model.
- The Storage screen rendered no models at all on an 80x24 terminal -- not even the table header. `DataTable { min-height: 3 }` lost two rows to its border and a third to a scrollbar gutter reserved globally, leaving zero content rows. The inventory now has a floor sized to its header plus rows, and an empty one says whether nothing is cached, the filter excluded everything, or the refresh failed.
- `scrollbar-gutter: stable` applied to `*` taxed every widget one row and one column for a scrollbar most of them could never show: a three-option list occupied six rows instead of five, and every bordered panel carried a dead column inside its right edge. The gutter is now scoped to the containers whose content actually grows and shrinks.
- The Settings screen's Save button and every message about saving sat below the fold on any terminal shorter than ~45 rows, so an invalid scaledown window, the unsaved-changes warning, and the second-esc-to-discard prompt were all written to a line nobody could see -- each looked like the key had done nothing. The form now fits, and feedback scrolls itself into view regardless.
- Footer hints were clipped mid-word rather than dropped: `i Details` rendered as `i D` on the main menu at 80 columns, `^l Clear log` as `^l Cl` on the monitor at 100. Hints that do not fit are now omitted and counted, with a marker pointing at the help overlay that lists all of them.
- The Hugging Face marker in the home auth block was a two-cell emoji among one-cell glyphs, and the diamonds marking Prime Intellect and Artificial Analysis are East Asian Width "Ambiguous" -- Rich measures one cell where a CJK-configured terminal draws two. All five markers are now unambiguously single-cell, so the rows line up in every locale.
- Result cards did not align their values (`Status  Healthy` and `Test command  curl ...` began at different columns) while the connection card beside them did. Both now measure the widest label. The deploy Profile Summary had the same defect in five of its rows, where the label was longer than the hand-counted padding assumed.
- The monitor offered `enter to retry` after a failed operation. Enter pops the screen exactly as esc and q do, and no retry path exists. The three different sentences describing how to leave that screen are now one.
- Switch settings distinguished on from off by colour alone, which the bundled monochrome theme and the low-colour terminals it exists for both flatten. Each toggle now states `On` or `Off` in words.
- The help overlay listed `ctrl+c` as "Copy selected text" -- Textual's own binding, shadowed by this app's priority binding on the same key -- and so never named the key that quits. It now describes the binding that actually runs, groups keys that share a description onto one row, and sizes its key column to the widest key instead of a fixed 12 that `ctrl+shift+c` overflowed.
- The status header reserved four rows to render one line, and its state markers varied between one and two cells so `state:` shifted sideways as the state changed.
- The Manage screen restated the footer's keys below its table and the Storage screen restated them in a tip; the main menu's subtitle stopped mid-phrase at narrow widths instead of wrapping.
- The Deployments screen and the Home deployment panel no longer report a provider outage as an empty fleet. Every provider listing was wrapped in a bare `except`, so a Modal CLI timeout or a Vast authentication failure simply removed those rows: a running, billing deployment silently vanished from the TUI, and the natural response to that is to deploy it a second time. Each provider now reports for itself, an unreachable one keeps the rows it last returned, and both screens name the provider, its error, and how old the rows they are showing are. A stale row stays selectable and stoppable, and nothing is pruned from OpenCode on the word of a provider that did not answer. A provider that is simply not configured reports nothing rather than an error.
- Fast Deploy no longer offers a placement whose provider publishes no hourly price. Modal lists none for H100 or H200, and those rows appeared as selectable `price n/a` options: they could not be ranked into a serving tier, and choosing one as a fallback gave the "at or below the approved hourly price" ceiling nothing to check against. They are excluded and counted in the status line, which now reports why placements were dropped instead of asserting a single reason for all of them. Advanced deploy still reaches that hardware.
- The abandoned-deployment warning now asks each provider what survived before alarming anyone. Journal entries were reported unconditionally and never cleared, so a deploy that had finished, been stopped from the CLI, or died with its provider kept warning on every launch -- with a spend figure -- for a resource that no longer existed. An entry a provider positively reports as gone is now resolved silently; one it still lists, or that could not be checked, is still reported. Warnings are capped so a backlog cannot bury the screen.
- Destroying a Vast rental now removes its SSH key along with its recovery record. Only `record.json` was deleted, so every rental left its private key, public key and `known_hosts` behind indefinitely; a local account that had rented 59 times was holding 47 private keys for hosts that no longer existed. The lock file is deliberately kept, because removal runs while that lock is held.
- A TUI crash now leaves a traceback in the debug log and exits non-zero. Textual renders an unhandled exception to a terminal it is about to restore and lets `run()` return normally, so the crash reached neither the log nor the exit status: a session that died mid-screen reported success and left an empty log behind. The log also records one line per session, so an empty file means nothing failed rather than that logging is broken.
- Vast rental startup requires a successful per-instance SSH key attachment and omits the reverted container startup hook, which caused SSH failures. Live rentals then certified vLLM serving on one GPU and on two-way tensor parallelism: the remaining `Connection refused` on a large image is Vast's sshd binding after the image pull, which the deploy loop already waits out.
- Vast live validation uses production-style SSH startup, checks total runtime and transfer estimates with cleanup headroom, and retains recovery records after uncertain image-probe creation. The Advanced deploy vision check supports vLLM without requiring a GGUF projector.
- Vast live certification covers llama.cpp text (with 1245 MiB verified resident on the device), llama.cpp image input, vLLM text, and two-way vLLM tensor parallelism against real rentals. Image input through vLLM is certified too, on an RTX A5000 through Advanced deploy. The vision stages verify the request path and a non-empty answer rather than visual accuracy, which `docs/vast-certification.md` states for both engines.
- Vast cleanup retries rate-limited account and instance identity checks, including reconciliation after uncertain creation, before destroying the rental.
- First llama.cpp Modal deploy after a large Hugging Face download no longer dies at the 30-minute web-server startup timeout. The GPU container sequentially hydrates GGUF shards (and a projector, if any) before `llama-server` starts, and the bind wait defaults to 90 minutes (`LLAMACPP_SERVE_STARTUP_TIMEOUT_MINUTES`).
